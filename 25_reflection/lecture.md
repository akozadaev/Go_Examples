## Введение: где заканчивается статическая информация

Начнём с главного свойства Go. Go - статически типизированный язык. Когда мы пишем `user.Name`, компилятор знает, что `user` имеет определённый тип, что у него существует поле `Name` и что выражение имеет, например, тип `string`. Если мы ошибёмся в имени поля или передадим строку вместо числа, программа не соберётся. Обычно это именно то, чего мы хотим.

Но теперь представим автора стандартного пакета `encoding/json`. Он должен написать функцию `Marshal`, прежде чем узнает о нашей структуре `User`. Более того, функция должна работать не только с `User`, но и с `Order`, `[]Product`, `map[string]any` и миллионами типов, которые появятся в чужих программах. Обычный интерфейс здесь помогает лишь частично. Можно потребовать от каждого типа метод `MarshalJSON`, но стандартная библиотека умеет сериализовать структуры и без такого метода.

Возникает задача: получить информацию о конкретном типе уже во время выполнения программы. Как называется структура? Какие у неё поля? Какие поля экспортированы? Какие теги прикреплены к этим полям? Каково значение каждого поля? Ответом служит reflection, то есть рефлексия или отражение.

Сегодня мы увидим два способа решить похожую проблему. Reflection исследует тип и значение во время выполнения. Кодогенерация исследует описание программы заранее и создаёт обычный статически типизированный код. В конце занятия мы сможем осознанно выбрать между интерфейсом, generics, reflection и генератором.

Есть ещё пакет `unsafe`. Он иногда упоминается рядом с reflection, потому что оба механизма позволяют выйти за рамки повседневной системы типов. Но цели у них разные. Reflection даёт проверяемый runtime-API для исследования типов. `unsafe` позволяет работать с представлением объектов в памяти и снимает часть защитных гарантий компилятора. Это не «более быстрая reflection» и не универсальный способ обходить ограничения языка.

# Часть I. Рефлексия

## 1. Интерфейсное значение как отправная точка

Посмотрим на простое объявление:

```go
var x any = 42
```

Переменная `x` имеет статический тип `any`, то есть `interface{}`. Внутри интерфейсного значения находятся два важных компонента: динамический тип `int` и динамическое значение `42`. Это не означает, что интерфейс буквально обязан быть реализован в памяти двумя машинными словами: внутреннее представление является деталью реализации. Для нашей модели достаточно знать пару «динамический тип - динамическое значение».

Пакет `reflect` даёт две главные точки входа:

```go
t := reflect.TypeOf(x)
v := reflect.ValueOf(x)
```

`reflect.TypeOf` возвращает описание динамического типа. `reflect.ValueOf` возвращает объект, через который можно исследовать динамическое значение. Почти весь API reflection строится вокруг `reflect.Type` и `reflect.Value`.

Сразу разберём важный случай с nil:

```go
var a any = nil
var p *int = nil
var b any = p
```

`a` - nil-интерфейс: у него нет ни динамического типа, ни динамического значения. `reflect.TypeOf(a)` вернёт `nil`, а `reflect.ValueOf(a)` - невалидный, нулевой `reflect.Value`.

`b` не является nil-интерфейсом. В нём есть динамический тип `*int`, хотя динамическое значение указателя равно nil. Поэтому `b == nil` даст `false`. `reflect.ValueOf(b)` будет валидным значением с kind `Pointer`, а его метод `IsNil()` вернёт `true`.

Это различие называют проблемой typed nil. На практике оно встречается, когда функция возвращает интерфейс ошибки:

```go
type MyError struct{}

func (*MyError) Error() string { return "ошибка" }

func f() error {
    var err *MyError
    return err
}
```

Результат `f()` не равен nil, потому что интерфейс содержит тип `*MyError`. Reflection не создаёт эту особенность, но позволяет её увидеть.

## 2. `reflect.Type`: тип, имя и категория

`reflect.Type` - интерфейс стандартной библиотеки, который описывает Go-тип. Начинающие часто смешивают понятия `Type` и `Kind`, поэтому разберём их отдельно.

Объявим новый именованный тип:

```go
type UserID int64

id := UserID(7)
t := reflect.TypeOf(id)

fmt.Println(t.String()) // main.UserID
fmt.Println(t.Name())   // UserID
fmt.Println(t.PkgPath())
fmt.Println(t.Kind())   // int64
```

Тип значения - `UserID`. У типа есть имя и пакет объявления. Но его базовая категория, kind, - `reflect.Int64`. Kind отвечает не на вопрос «какой это точный тип?», а на вопрос «какой набор операций к нему применим?». И у `int64`, и у `UserID` kind будет `Int64`. У `User`, `Order` и любой другой структуры kind будет `Struct`.

В `reflect` определены категории `Bool`, семейства `Int` и `Uint`, `Float32`, `Float64`, `Complex64`, `Complex128`, `Array`, `Chan`, `Func`, `Interface`, `Map`, `Pointer`, `Slice`, `String`, `Struct`, `UnsafePointer` и несколько служебных значений. В современном API используется имя `Pointer`; старое строковое сокращение `Ptr` иногда встречается в старых материалах и названиях методов.

Многие методы `reflect.Type` допустимы только для определённого kind. `Elem()` можно применять к массиву, каналу, map, указателю или slice; для других типов метод вызовет панику. `NumField()` допустим для структуры, `NumIn()` и `NumOut()` - для функции, `Key()` - для map. Reflection не отменяет типовые правила, а переносит их проверку во время выполнения.

Поэтому хороший рефлексивный код сначала классифицирует тип:

```go
func describe(x any) {
    t := reflect.TypeOf(x)
    if t == nil {
        fmt.Println("nil interface")
        return
    }

    fmt.Printf("type=%v kind=%v\n", t, t.Kind())

    switch t.Kind() {
    case reflect.Struct:
        fmt.Println("fields:", t.NumField())
    case reflect.Slice, reflect.Array:
        fmt.Println("element type:", t.Elem())
    case reflect.Map:
        fmt.Println("key:", t.Key(), "value:", t.Elem())
    case reflect.Func:
        fmt.Println("inputs:", t.NumIn(), "outputs:", t.NumOut())
    }
}
```

Здесь нет общего исключения или ошибки от `reflect`: неверное применение метода обычно заканчивается panic. Библиотечный код должен сам проверить предусловия и вернуть вызывающему осмысленную ошибку.

### Тип интерфейса и `TypeFor`

Интерфейсные типы не существуют как runtime-значения сами по себе. Исторически, чтобы получить `reflect.Type` для `io.Writer`, использовали такую идиому:

```go
writerType := reflect.TypeOf((*io.Writer)(nil)).Elem()
```

Мы создаём nil-указатель на интерфейс и берём тип его элемента. Начиная с Go 1.22 можно выразить намерение прямо:

```go
writerType := reflect.TypeFor[io.Writer]()
fileType := reflect.TypeFor[*os.File]()

fmt.Println(fileType.Implements(writerType)) // true
```

`TypeFor[T]` особенно полезен в generic-коде и в реестрах, где тип известен на этапе компиляции, но нужен в форме `reflect.Type`.

### Сравнение и совместимость типов

Reflection позволяет задать три разных вопроса, которые не следует смешивать.

`t1.AssignableTo(t2)` проверяет, можно ли значение типа `t1` присвоить переменной типа `t2` без явного преобразования. `t1.ConvertibleTo(t2)` проверяет, разрешено ли преобразование языка Go. `t.Implements(interfaceType)` проверяет, реализует ли тип интерфейс.

```go
type UserID int64

userIDType := reflect.TypeFor[UserID]()
int64Type := reflect.TypeFor[int64]()

fmt.Println(userIDType.AssignableTo(int64Type))  // false
fmt.Println(userIDType.ConvertibleTo(int64Type)) // true
```

Если тип реализует интерфейс только методами с pointer receiver, проверять нужно указательный тип:

```go
type Saver interface { Save() error }

// Если Save объявлен как func (*User) Save() error,
// reflect.TypeFor[User]().Implements(...) даст false,
// а reflect.TypeFor[*User]().Implements(...) - true.
```

Это проявление method set: набор методов `T` и `*T` различается. Reflection честно отражает правила спецификации, а не угадывает намерение автора.

### Поля и методы в Go 1.26

До Go 1.26 поля структуры обычно перебирали индексами:

```go
for i := 0; i < t.NumField(); i++ {
    field := t.Field(i)
    fmt.Println(field.Name, field.Type)
}
```

В Go 1.26 появились методы-итераторы `Type.Fields`, `Type.Methods`, `Type.Ins` и `Type.Outs`. Они сочетаются с `range` над итераторами:

```go
for field := range t.Fields() {
    fmt.Println(field.Name, field.Type)
}
```

Для значений добавлены `Value.Fields` и `Value.Methods`. `Value.Fields` выдаёт одновременно описание поля и соответствующее значение. Старые индексные методы остаются частью API и нужны, в частности, для совместимости кода с предыдущими версиями Go.

## 3. `reflect.Value`: чтение значения

`reflect.Value` - не само пользовательское значение, а дескриптор, через который пакет выполняет операции. У него есть `Type()` и `Kind()`, методы чтения, проверки и изменения.

```go
x := 42
v := reflect.ValueOf(x)

fmt.Println(v.Type())      // int
fmt.Println(v.Kind())      // int
fmt.Println(v.Int())       // 42
fmt.Println(v.Interface()) // 42 как значение типа any
```

Методы чтения сгруппированы по kind. `Int()` работает для всех знаковых целых типов и возвращает `int64`; `Uint()` - `uint64`; `Float()` - `float64`; `Complex()` - `complex128`. `String()` заслуживает осторожности: для string-значения он возвращает содержимое, но для других kind может возвращать диагностическое представление вида `<int Value>`. Для универсального форматирования обычно получают `Interface()` и передают его в `fmt`, предварительно проверив `CanInterface()`.

### Валидность

Нулевой `reflect.Value` ничего не представляет:

```go
var v reflect.Value
fmt.Println(v.IsValid()) // false
```

Невалидное значение возвращают `ValueOf(nil)`, `MapIndex` для отсутствующего ключа, `FieldByName` для отсутствующего поля и `MethodByName` для отсутствующего метода. Метод `IsValid` разрешено вызвать всегда. Большинство остальных методов невалидного значения паникуют.

Отсюда важный шаблон:

```go
field := v.FieldByName("Age")
if !field.IsValid() {
    return fmt.Errorf("field Age not found")
}
```

Не путайте невалидный `Value` с валидным нулевым значением типа. `reflect.Zero(reflect.TypeFor[int]())` создаст валидное значение `int`, равное нулю. Проверить нулевое значение можно методом `IsZero`, но он также требует валидного `Value`.

### `Interface` и экспортированность

`Interface()` возвращает обычное значение с исходным динамическим типом. Но получать интерфейсное представление неэкспортированного поля из другого контекста запрещено. Проверка `CanInterface()` позволяет не получить panic.

```go
if field.CanInterface() {
    fmt.Printf("%v\n", field.Interface())
}
```

Reflection позволяет увидеть имя и тип неэкспортированного поля, потому что это метаданные типа, но не даёт легального обхода правил доступа к его содержимому. Попытки сочетать reflection и `unsafe`, чтобы читать приватные поля чужих пакетов, создают хрупкую зависимость от реализации и почти всегда являются ошибкой проектирования.

## 4. Адресуемость и изменение значений

Следующий вопрос: почему нельзя просто вызвать `SetInt`?

```go
x := 42
v := reflect.ValueOf(x)
v.SetInt(24) // panic
```

Когда `x` упакован в интерфейс для передачи в `ValueOf`, reflection получает копию значения. Эта копия не является изменяемым местом хранения исходной переменной. Метод `CanSet()` вернёт false.

Чтобы изменить исходную переменную, передаём указатель и разыменовываем его:

```go
x := 42
v := reflect.ValueOf(&x)
elem := v.Elem()

fmt.Println(elem.CanAddr()) // true
fmt.Println(elem.CanSet())  // true
elem.SetInt(24)
fmt.Println(x)              // 24
```

`CanAddr` означает, что у представленного значения можно получить адрес. `CanSet` означает, что его разрешено изменить через reflection. Адресуемость необходима, но сама по себе не всегда достаточна: неэкспортированное поле может быть адресуемым, но не устанавливаемым.

Универсальный `Set` требует значение присваиваемого типа:

```go
dst := reflect.ValueOf(&x).Elem()
src := reflect.ValueOf(100)
dst.Set(src)
```

Если `src.Type()` не assignable к `dst.Type()`, будет panic. Если допустимо явное преобразование, его надо выполнить через `Convert`:

```go
type Score int

score := Score(0)
dst := reflect.ValueOf(&score).Elem()
src := reflect.ValueOf(100)

if src.Type().ConvertibleTo(dst.Type()) {
    dst.Set(src.Convert(dst.Type()))
}
```

Нельзя автоматически считать любую числовую конверсию безопасной: преобразование большого `int64` в `int8` разрешено языком, но изменяет значение. Reflection проверяет допустимость операции, а бизнес-правило диапазона остаётся обязанностью программы.

`Elem()` применяют к указателю или интерфейсному значению. Для nil-указателя он вернёт невалидный `Value`. Функция `reflect.Indirect(v)` ведёт себя подобно разыменованию указателя и тоже возвращает нулевой `Value` для nil. В рекурсивном коде всегда должен существовать явный план обработки nil.

[Демонстрация, 3 минуты. Запустите `go run main_valueof.go`. Перед запуском спросите, почему `ValueOf(x).SetInt` не работает, а `ValueOf(&x).Elem().SetInt` работает.]

## 5. Создание значений во время выполнения

Reflection умеет не только исследовать, но и создавать значения. `reflect.New(t)` создаёт указатель на новое нулевое значение типа `t`. `reflect.Zero(t)` возвращает нулевое значение. `MakeSlice`, `MakeMap`, `MakeChan` создают соответствующие runtime-объекты.

```go
userType := reflect.TypeFor[User]()
ptr := reflect.New(userType) // *User
user := ptr.Elem()           // User

user.FieldByName("Name").SetString("Анна")
user.FieldByName("Age").SetInt(30)

created := ptr.Interface().(*User)
```

В данном примере приведение `.(*User)` безопасно, потому что тип создан нами и заранее известен. В действительно универсальной фабрике результат останется `any` или будет проверен против ожидаемого интерфейса.

Слайс можно создать так:

```go
sliceType := reflect.SliceOf(reflect.TypeFor[string]())
slice := reflect.MakeSlice(sliceType, 0, 4)
slice = reflect.Append(slice, reflect.ValueOf("Go"))
slice = reflect.Append(slice, reflect.ValueOf("1.26"))
```

Есть конструкторы типов `PointerTo`, `SliceOf`, `MapOf`, `ArrayOf`, `ChanOf`, `FuncOf` и даже `StructOf`. Они нужны инфраструктурным библиотекам, но редко должны попадать в бизнес-код. Чем больше типов программа конструирует динамически, тем меньше помощи даёт компилятор.

## 6. Структуры и теги

Структурные теги - строковые метаданные, являющиеся частью типа поля:

```go
type User struct {
    ID       int    `json:"id" db:"user_id"`
    Name     string `json:"name,omitempty"`
    Password string `json:"-"`
    token    string
}
```

`reflect.StructField` содержит `Name`, `Type`, `Tag`, `Anonymous`, индексный путь `Index` и `PkgPath`. Метод `IsExported()` сообщает экспортированность. `Tag.Get("json")` возвращает значение тега, а `Tag.Lookup("json")` дополнительно сообщает, присутствовал ли ключ. `Lookup` нужен, если отсутствующий тег и тег с пустым значением имеют разный смысл.

Тег является строкой по соглашению. Пакет `reflect` не знает семантику `json`, `db` или `validate`; её задаёт конкретная библиотека. В значении `json:"name,omitempty"` имя и опции ещё надо разобрать. Тег `json:"-"` обычно означает исключение поля. Неверно сформированный тег может пройти компиляцию, поэтому для проверки полезен `go vet`.

Упрощённый сериализатор может выглядеть так:

```go
func toMap(input any) (map[string]any, error) {
    v := reflect.ValueOf(input)
    if !v.IsValid() {
        return nil, errors.New("nil input")
    }
    if v.Kind() == reflect.Pointer {
        if v.IsNil() {
            return nil, errors.New("nil pointer")
        }
        v = v.Elem()
    }
    if v.Kind() != reflect.Struct {
        return nil, fmt.Errorf("want struct, got %s", v.Kind())
    }

    result := make(map[string]any)
    for sf, fv := range v.Fields() {
        if !sf.IsExported() || !fv.CanInterface() {
            continue
        }
        name, options, _ := strings.Cut(sf.Tag.Get("json"), ",")
        if name == "-" {
            continue
        }
        if name == "" {
            name = sf.Name
        }
        if options == "omitempty" && fv.IsZero() {
            continue
        }
        result[name] = fv.Interface()
    }
    return result, nil
}
```

Это всё ещё не полноценный JSON-кодировщик. Не обработаны вложенные значения, встраивание полей, конфликты имён, несколько опций, циклические указатели, пользовательские `Marshaler`, специальные правила строк и чисел. Этот список полезен: он показывает, почему универсальные библиотеки reflection сложнее демонстрационного цикла из десяти строк.

`reflect.VisibleFields` помогает получить поля структуры с учётом продвижения встроенных полей. `FieldByIndex` обращается к полю по индексному пути. Но точные правила конфликтов и тегов всё равно определяет библиотека. Если вы имитируете `encoding/json`, нужно изучать и тестировать именно его контракт.

[Демонстрация, 4 минуты. Запустите `go run main_struct.go`, затем `go run main_serialize.go`. Обратите внимание, что учебный сериализатор выводит map в неопределённом порядке. Покажите, какие ограничения перечислены выше.]

## 7. Слайсы, массивы, map и интерфейсы

Для массива и слайса доступны `Len`, `Index`, а для слайса ещё `Cap`, `Slice` и `SetLen`. Элемент изменяемого слайса обычно устанавливаем, даже если сам заголовок слайса был передан по значению:

```go
items := []int{10, 20, 30}
v := reflect.ValueOf(items)
v.Index(1).SetInt(99)
fmt.Println(items) // [10 99 30]
```

Причина в том, что копия заголовка слайса указывает на тот же backing array. Но изменить длину исходной переменной `items` через эту копию нельзя; для этого нужен адрес переменной.

Map исследуют через `MapIndex`, `MapRange` или `Seq2`-итератор. Отсутствующий ключ даёт невалидный `Value`. Значение элемента map неадресуемо, поэтому нельзя получить `MapIndex` и вызвать у результата `Set`. Изменяют map через `SetMapIndex`:

```go
m := map[string]int{"a": 1}
v := reflect.ValueOf(m)
v.SetMapIndex(reflect.ValueOf("b"), reflect.ValueOf(2))

// Удаление ключа - установка невалидного Value.
v.SetMapIndex(reflect.ValueOf("a"), reflect.Value{})
```

Для каналов существуют `Send`, `Recv`, `TrySend`, `TryRecv` и `reflect.Select`. `reflect.Select` позволяет динамически собрать набор select-case, число которых неизвестно во время компиляции. Это мощный, но редкий инструмент: обычный `select` предпочтительнее, когда набор каналов статичен.

## 8. Функции и методы

Функция тоже является значением:

```go
func Sum(a, b int) int { return a + b }

fn := reflect.ValueOf(Sum)
results := fn.Call([]reflect.Value{
    reflect.ValueOf(10),
    reflect.ValueOf(20),
})
fmt.Println(results[0].Int()) // 30
```

`Call` принимает слайс аргументов и возвращает слайс результатов. Неверное количество аргументов, несовместимый тип или вызов не-функции приводит к panic. В универсальном диспетчере сигнатуру заранее проверяют через `Type.NumIn`, `In`, `NumOut`, `Out` и `IsVariadic`.

Для variadic-функции есть два режима. `Call` получает каждый вариативный аргумент отдельно. `CallSlice` получает на последней позиции один слайс, аналогично обычному вызову `f(slice...)`.

Метод можно получить через `MethodByName`. Если метод получен от значения, receiver уже связан:

```go
calc := &Calculator{}
method := reflect.ValueOf(calc).MethodByName("Add")
if !method.IsValid() {
    return errors.New("method Add not found")
}
result := method.Call([]reflect.Value{
    reflect.ValueOf(2),
    reflect.ValueOf(3),
})
```

Имя метода здесь строковое. Компилятор не заметит его переименование, поэтому такие вызовы требуют тестов. Кроме того, динамический `MethodByName` может заставить linker сохранить больше методов и увеличить бинарный файл. Если операции известны заранее, `map[string]func` или интерфейс обычно проще.

`reflect.MakeFunc` решает обратную задачу: создаёт функцию заданного типа на основе универсального обработчика `func([]reflect.Value) []reflect.Value`. Его используют адаптеры и RPC-библиотеки, но он требует особенно строгой проверки сигнатур.

[Демонстрация, 4 минуты. Запустите `go run main_call.go`. Покажите разницу `Call` и `CallSlice`. Затем спросите: «Если имена Add, Subtract и Multiply известны в исходнике, нужна ли здесь reflection в production-коде?»]

## 9. Сравнение значений

Для comparable-значений в современном API существуют `Value.Comparable` и `Value.Equal`. Перед `Equal` нужно убедиться, что сравнение допустимо; несравнимые динамические типы могут вызвать panic.

`reflect.DeepEqual` рекурсивно сравнивает значения и исторически широко применялся в тестах. Но его семантика не всегда совпадает с предметным равенством: nil-слайс и пустой слайс различны; функции равны только если обе nil; значения времени могут содержать внутреннее состояние, которое не должно участвовать в бизнес-сравнении. В новом коде тестов часто удобнее специализированные сравнения или `cmp` из `github.com/google/go-cmp` с явными опциями.

`reflect.Swapper(slice)` возвращает функцию перестановки элементов неизвестного типа. Сегодня многие алгоритмы проще написать с generics, но этот API остаётся примером runtime-обобщения.

## 10. Три закона reflection

Теперь сформулируем классические законы.

Первый: от интерфейсного значения можно перейти к объектам reflection - `TypeOf` и `ValueOf` извлекают динамические тип и значение.

Второй: от `reflect.Value` можно вернуться к интерфейсному значению через `Interface`, если доступ разрешён.

Третий: чтобы изменить отражённый объект, значение должно быть устанавливаемым. Обычно это означает, что мы передали указатель, разыменовали его и работаем с экспортированной, адресуемой частью объекта.

Эти законы хорошо объясняют устройство API, но в практическом коде к ним добавляются проверки: значение валидно; операция разрешена для kind; nil обработан; тип assignable или осознанно convertible; поле доступно; индекс находится в диапазоне.

## 11. Плюсы, минусы и производительность

Reflection полезна, когда множество типов действительно открыто и становится известно только во время выполнения. Она позволяет создать один сериализатор, валидатор, RPC-диспетчер или диагностический инструмент. Она умеет читать структурные теги и сигнатуры без требования реализовать специальный интерфейс каждым пользовательским типом.

Цена состоит из нескольких частей.

Первая цена - потеря статических гарантий. `FieldByName("Nmae")` с опечаткой компилируется. Ошибка проявится только на соответствующем пути выполнения.

Вторая - сложность. Код заполнен проверками kind, валидности и устанавливаемости. Пропущенная проверка часто приводит к panic, а не к обычной ошибке.

Третья - сопровождение. IDE и рефакторинг не всегда видят строковые имена. Поиск использований метода не покажет `MethodByName` с вычисляемой строкой.

Четвёртая - runtime-стоимость. Динамическая диспетчеризация, упаковка в интерфейсы и создание промежуточных `reflect.Value` могут быть дороже прямого доступа и иногда создают аллокации. Но утверждение «reflection всегда медленная» недостаточно точно. Если операция выполняется один раз при старте приложения или окружена сетевым I/O, разница может не иметь значения.

Типичная оптимизация инфраструктурной библиотеки - один раз построить план для каждого `reflect.Type`, а затем кэшировать его. Например, сериализатор заранее вычисляет список экспортированных полей, их индексные пути, имена и функции кодирования. На каждом объекте он применяет готовый план, а не повторяет полное исследование структуры. Кэш часто организуют через `sync.Map` или обычную map под mutex. Его ключом может быть `reflect.Type`, поскольку значения `Type` сравнимы.

Оптимизация должна опираться на benchmark и профиль. Сравнивать нужно одинаковую семантику и реальные данные. Кодогенерация, которую мы изучим после перерыва, может убрать reflection из горячего пути, но добавляет сложность сборки.

Хорошее архитектурное правило: локализовать reflection на границе системы. Рефлексивный слой проверяет неизвестный вход и превращает его в типизированный внутренний план. Бизнес-логика после этой границы работает с обычными типами.

Перед выбором reflection задайте вопросы:

1. Можно ли выразить требуемое поведение интерфейсом?
2. Известен ли небольшой закрытый набор типов для type switch?
3. Одинаков ли алгоритм для семейства типов, то есть подходят ли generics?
4. Известны ли формы во время сборки и можно ли сгенерировать статический код?
5. Действительно ли тип становится известен только в runtime?

Если на последний вопрос ответ «да», reflection, вероятно, оправдана.

# Часть II. Пакет `unsafe`

## 12. Что именно делает `unsafe`

Пакет `unsafe` имеет особый статус. Его API компилятор понимает специально, а гарантии переносимости слабее, чем у обычного Go-кода. Документация прямо говорит, что пакет позволяет обходить типовую безопасность и что код может быть непереносимым.

Главный тип - `unsafe.Pointer`. Любой указатель `*T` можно преобразовать в `unsafe.Pointer`, а `unsafe.Pointer` - в указатель другого типа при соблюдении разрешённых правил. Но сам факт, что компилятор принял преобразование, не означает корректность чтения памяти.

```go
var x int32 = 42
p := unsafe.Pointer(&x)
value := *(*int32)(p)
fmt.Println(value)
```

Здесь мы вернулись к исходному типу и читаем объект в его границах. А такое чтение недопустимо:

```go
// Нельзя делать так:
// bad := *(*float64)(p)
```

`float64` требует восемь байт, объект `x` занимает четыре. Мы вышли бы за границу объекта. `unsafe` отключает часть проверок типов, но не делает произвольный адрес валидным.

## 13. Размер, выравнивание и смещение

`unsafe.Sizeof(x)` возвращает размер представления значения в байтах. `unsafe.Alignof(x)` - требование выравнивания. `unsafe.Offsetof(s.Field)` - смещение поля внутри структуры.

```go
type Example struct {
    A int32
    B int64
    C int32
}
```

На типичной 64-битной архитектуре между полями может появиться padding, чтобы `B` было правильно выровнено. Поэтому размер структуры может превышать сумму размеров её полей. Конкретные значения нужно измерять на целевой архитектуре, а не запоминать как свойство языка.

`Sizeof` не проходит по графу объектов. Размер строки - размер её дескриптора, а не количество байт текста. Размер слайса - размер заголовка, а не backing array. Размер map не включает все бакеты.

[Демонстрация, 3 минуты. Запустите `go run main_unsafe.go` и сравните `Sizeof`, `Alignof` и `Offsetof`. Обратите внимание на padding структуры.]

## 14. Почему `uintptr` не является указателем

`uintptr` - целое число, достаточно большое для хранения битового представления адреса. Но для garbage collector это число, а не ссылка на объект. Пока адрес хранится только как `uintptr`, объект не обязан считаться достижимым.

Поэтому опасно разбивать преобразование и арифметику на несколько выражений:

```go
base := uintptr(unsafe.Pointer(&s))
// Между строками объект может перестать считаться живым.
field := unsafe.Pointer(base + offset)
```

Документация разрешает определённые шаблоны, где преобразование туда и обратно находится в одном выражении, но современный и более ясный инструмент для смещения - `unsafe.Add`:

```go
base := unsafe.Pointer(&s)
field := unsafe.Add(base, unsafe.Offsetof(s.B))
b := *(*int64)(field)
```

Даже `unsafe.Add` не разрешает сформировать указатель за пределами исходного объекта и разыменовать его. В отличие от C, Go не обещает произвольную адресную арифметику.

`runtime.KeepAlive(x)` может гарантировать, что объект считается живым до конкретной точки, когда низкоуровневый вызов хранит адрес способом, невидимым сборщику мусора. Это не универсальный «ремонт» ошибочного `uintptr`-кода. Сначала нужно следовать документированному шаблону конкретного API, а `KeepAlive` ставить после последнего внешнего использования ресурса.

## 15. Современные помощники `unsafe`

`unsafe.Slice(ptr, len)` создаёт слайс над памятью, начинающейся с указателя на элемент. Память должна содержать достаточное число корректно выровненных элементов и оставаться живой всё время использования слайса.

`unsafe.String(ptr, len)` создаёт строку над существующими байтами без копирования. Эти байты нельзя менять, пока существует строка: строки в Go логически неизменяемы, и нарушение этого ожидания может привести к гонкам и некорректному поведению.

> **Критическое условие безопасности.** Значение, из которого получены `ptr`, строка или слайс, обязано оставаться живым всё время их использования. Область памяти должна иметь достаточный размер и правильное выравнивание, а память, доступная через `unsafe.String`, нельзя изменять. `unsafe.String` и `unsafe.Slice` не управляют владением и временем жизни данных. Нарушение любого из этих условий может дать повреждение памяти или data race, даже если программа успешно компилируется и иногда проходит тесты.

`unsafe.StringData(s)` возвращает указатель на байты строки, а `unsafe.SliceData(slice)` - указатель на первый элемент слайса с документированным поведением для nil и пустых значений. Эти функции лучше старых ручных преобразований через самодельные заголовки `reflect.StringHeader` и `reflect.SliceHeader`. Поля `Data` в старых header-типах имеют тип `uintptr`, не гарантируют удержание памяти живой и не должны использоваться как общий рецепт конвертации.

Безопасная операция

```go
text := string(bytes)
```

обычно создаёт копию и разрывает связь с изменяемым слайсом. Zero-copy вариант может быть быстрее, но связывает времена жизни объектов и требует неизменности исходных байтов. Выбирать его можно только после измерения, при чётко описанном владении памятью.

Реальные области применения `unsafe` - системные вызовы, взаимодействие с C, memory-mapped структуры, runtime и тщательно измеренные внутренности высокопроизводительной библиотеки. Неудачные причины - доступ к приватному полю, экономия одной строки преобразования или предположение, что «так быстрее» без профиля.

Перед добавлением `unsafe` полезно выполнить `go vet`, тесты с `-race`, тесты на всех целевых архитектурах и проверить правила указателей утилитой `checkptr`, которую компилятор использует при соответствующем режиме диагностики. Но ни один инструмент не доказывает корректность произвольного unsafe-кода.

На этом первая половина закончена. Reflection позволяет динамически исследовать типы, сохраняя проверяемый API, хотя многие ошибки переносятся в runtime. `unsafe` работает с представлением памяти и требует намного более строгого доказательства корректности.

# Часть III. Кодогенерация

## 16. Основная идея

Вернёмся к сериализатору. Reflection позволяет одному коду обработать любую структуру, но на каждом запуске приходится работать через динамический API. А что, если конкретные структуры известны при сборке? Мы можем написать программу, которая прочитает их определения и создаст функции вроде `MarshalUser`, обращающиеся прямо к `user.ID` и `user.Name`.

Кодогенерация - автоматическое создание исходного кода из другого описания. Входом может быть Go AST, protobuf-схема, OpenAPI-документ, SQL-запрос, таблица enum или шаблон. Выходом является обычный исходный файл, который затем проверяет компилятор.

В Go генератор не является макросом и не работает скрыто внутри компилятора. Это отдельная программа. Она читает вход, создаёт файл и завершается. `go build` видит результат так же, как ручной код. В production-процессе генератор обычно не запускается и не добавляет runtime-стоимость.

Преимущества:

- повторяющийся код создаётся единообразно;
- выход остаётся типизированным и проверяется компилятором;
- reflection можно убрать из горячего пути;
- изменение схемы приводит к воспроизводимому обновлению всех зависимых методов;
- сгенерированный код можно читать, тестировать и профилировать.

Недостатки:

- появляется дополнительный инструмент и его версия;
- сборочный процесс усложняется;
- большие generated-файлы создают шум в diff;
- ошибка генератора размножается во всех результатах;
- разработчику иногда приходится отлаживать сразу вход, генератор и выход;
- generated API может мешать обычному рефакторингу.

Небольшую функцию обычно проще написать вручную. Generics лучше, если весь повтор можно выразить одним статическим алгоритмом. Кодогенерация оправдана, когда повторение существенно, формы известны при сборке, а результат должен быть обычным типобезопасным кодом.

## 17. Директива `go:generate`

Стандартная команда `go generate` ищет в Go-файлах директивы следующего вида:

```go
//go:generate stringer -type=Status
```

После `//` нельзя ставить пробел: `// go:generate` - обычный комментарий. Директива должна находиться на отдельной строке. Команда запускается из каталога пакета.

Самое важное свойство: `go generate` не запускается автоматически командами `go build`, `go test` или `go install`. Генерация - явно инициируемое действие. Обычная сборка не должна неожиданно менять рабочее дерево.

`go generate` не является командной оболочкой. Оно разделяет строку на аргументы, понимает двойные кавычки в синтаксисе Go и выполняет программу напрямую. Конвейер `|`, перенаправление `>` и `&&` не получают shell-семантику без явного запуска оболочки, а такой запуск уменьшает переносимость между операционными системами.

Во время выполнения доступны специальные переменные:

- `$GOFILE` - имя файла с директивой;
- `$GOLINE` - номер строки;
- `$GOPACKAGE` - имя пакета;
- `$GOOS` и `$GOARCH` - целевая платформа;
- `$DOLLAR` - символ доллара.

Полезные команды:

```bash
go generate -n ./...             # только показать команды
go generate -x ./...             # печатать команды при выполнении
go generate -run stringer ./...  # оставить совпавшие директивы
go generate -skip easyjson ./... # исключить совпавшие директивы
```

Пакеты обрабатываются последовательно в указанном порядке; внутри пакета файлы идут по имени, внутри файла директивы - сверху вниз. Если команда завершилась с ошибкой, оставшиеся директивы этого пакета пропускаются. Но `go generate` не является полноценной build system: оно не строит граф выходов, не сравнивает время файлов и не кэширует генерацию.

[Демонстрация, 2 минуты. В каталоге кодогенерации выполните `go generate -n ./...`. Покажите, что `-n` ничего не изменяет и позволяет увидеть план.]

### Маркер generated-файла

До первого обычного текста generated-файл должен содержать строку, совпадающую с канонической формой:

```go
// Code generated by mapper; DO NOT EDIT.
```

Слова до `DO NOT EDIT` могут различаться, но сама форма важна. Её распознают Go-инструменты и системы анализа. Маркер говорит, что ручная правка результата будет потеряна при следующем запуске. Исправлять следует источник или генератор.

### Нужно ли коммитить результат

Для Go-проектов сгенерированные `.go`-файлы обычно коммитят. Тогда пользователь библиотеки и обычная сборка не зависят от наличия генератора. Pull request показывает изменение публичного кода, а CI может проверить актуальность результата.

Распространённая CI-проверка:

1. получить чистую копию репозитория;
2. запустить генерацию фиксированной версией инструментов;
3. запустить форматирование и тесты;
4. убедиться, что рабочее дерево не изменилось.

Если появился diff, автор изменил вход, но забыл обновить generated-файлы, либо генерация недетерминирована.

## 18. Воспроизводимость инструментов

Директива с голым именем `stringer` зависит от `PATH`. Команда установки с `@latest` означает «возьми актуальную версию сегодня», поэтому через полгода она может создать другой файл. Для демонстрации это допустимо, для production-сборки - нет.

Версию генератора фиксируют одним из способов. Можно вызывать `go run module/path@version` прямо из директивы. В современных Go-модулях можно добавить инструмент как tool dependency в `go.mod` и запускать через `go tool`. Можно поддерживать отдельный модуль `tools`, контейнер или Makefile с конкретными версиями. Важно не конкретное оформление, а свойства: версия видна, одинаково устанавливается локально и в CI, обновляется отдельным осознанным изменением.

Генератор должен быть детерминирован. При одинаковых входах и версии он обязан производить одинаковые байты. Нельзя без необходимости добавлять текущее время, случайные идентификаторы, имя пользователя и абсолютный путь. Если данные собраны из map, ключи сортируют. Импорты и объявления выводят в стабильном порядке.

Результат следует сначала полностью сформировать в памяти, затем пропустить через `go/format`, а после успеха записать. Для надёжного инструмента запись делают атомарно через временный файл в той же директории и переименование. Ошибка не должна оставлять наполовину записанный Go-файл.

## 19. `stringer`

В Go перечисления обычно представлены именованным целочисленным типом и константами:

```go
type Status int

const (
    StatusPending Status = iota
    StatusInProgress
    StatusCompleted
    StatusCancelled
)
```

Без метода `String` форматирование покажет число. Инструмент `golang.org/x/tools/cmd/stringer` анализирует константы и создаёт:

```go
func (s Status) String() string
```

Директива находится рядом с типом:

```go
//go:generate stringer -type=Status
```

Сгенерированный метод удовлетворяет `fmt.Stringer`, поэтому `fmt.Println(StatusPending)` печатает имя.

Последовательный `iota` удобен, но не обязателен: `stringer` умеет обрабатывать разреженные значения. Если несколько констант имеют одно число, строковое представление неоднозначно, и инструмент выбирает одно имя по своим документированным правилам. Флаг `-trimprefix=Status` убирает общий префикс, а `-linecomment` позволяет использовать текст комментария.

Нужно различать диагностическое имя и стабильный протокол. Если `StatusPending.String()` автоматически становится JSON-значением или полем базы данных, простое переименование Go-константы меняет внешний контракт. Для публичного API строки лучше задать явно и покрыть тестами.

[Демонстрация, 3 минуты. Откройте `stringer_example/status.go` и `status_string.go`, затем запустите `go run ./cmd/stringer`. Покажите, что generated-код - обычный Go, а не runtime-магия.]

## 20. `jsonenums`

Стандартный `encoding/json` кодирует именованный `int` как число, если тип не реализует специальные интерфейсы. Для API часто хочется строку `"PriorityHigh"`. Генератор `jsonenums` создаёт методы `MarshalJSON` и `UnmarshalJSON`.

При декодировании особенно важно поведение для неизвестной строки. Молчаливое превращение в нулевое значение скрывает ошибку клиента. Хорошая реализация возвращает ошибку, содержащую имя типа и неизвестное значение.

Проект `github.com/campoy/jsonenums` полезен как учебный пример, но внешнюю зависимость надо оценивать по активности сопровождения, лицензии, совместимости с текущим Go и точной семантике результата. Маленький публичный enum часто разумнее реализовать вручную или генерировать собственным компактным инструментом, потому что его JSON-строки являются частью контракта.

[Демонстрация, 2 минуты. Запустите `go run ./cmd/jsonenums`. Обратите внимание на успешное кодирование четырёх значений и ошибку для строки `"invalid"`.]

## 21. `easyjson` и честный benchmark

`easyjson` создаёт специализированные кодировщики и декодировщики для структур. Вместо обхода полей через reflection generated-код обращается к полям напрямую и пишет JSON специализированным lexer/writer API.

Потенциальные преимущества - меньше динамической работы и аллокаций. Но нельзя обещать универсальное ускорение «в четыре раза». Результат зависит от формы данных, операции, версии Go, архитектуры и настроек. Его измеряют:

```bash
go test -bench=. -benchmem ./easyjson_example
```

Смотрят `ns/op`, `B/op`, `allocs/op` и обязательно проверяют корректность JSON. Один быстрый неправильный кодировщик не является оптимизацией.

В benchmark легко допустить тонкую ошибку. Если `easyjson` уже создал для `User` метод `MarshalJSON`, то вызов `encoding/json.Marshal(user)` обнаружит интерфейс `json.Marshaler` и вызовет тот же generated-метод. Это было бы сравнением easyjson с самим собой. Поэтому `easyjson_example/benchmark_test.go` содержит отдельные зеркальные типы `plainUser` и `plainProfile` с теми же полями и тегами, но без generated-методов. Стандартный путь работает именно с ними.

То же относится к `UnmarshalJSON`: стандартный benchmark декодирует в `plainUser`. Отдельный тест `TestJSONImplementationsAreEquivalent` перед измерением проверяет семантическую эквивалентность результатов. Benchmark сообщает аллокации, не позволяет компилятору отбросить результат и завершает тест при неожиданной ошибке. Так сравниваются разные реализации одинаковой задачи, а не просто две строки кода с похожими названиями.

У специализированного генератора могут отличаться пограничные правила: неизвестные поля, регистр имён, `omitempty` и `omitzero`, пользовательские маршалеры, точность чисел, streaming. Перед заменой `encoding/json` нужны compatibility-тесты на контракт конкретного сервиса.

## 22. `impl` и границы автоматизации

Инструмент `impl` создаёт заготовки методов, необходимых конкретному receiver для реализации интерфейса. Он удобен, когда интерфейс велик:

```text
impl 'recv *FileLogger' impl_example.Logger
```

Но генератор знает только сигнатуры. Он не знает, что означает корректно записать сообщение, как обработать ошибку диска или нужна ли синхронизация. Сгенерированную заглушку следует рассматривать как старт ручной реализации, а не как готовую бизнес-логику.

После реализации полезна compile-time проверка:

```go
var _ Logger = (*FileLogger)(nil)
```

Она ничего не выполняет, но заставляет компилятор подтвердить соответствие интерфейсу.

Другие распространённые классы генераторов: protobuf и gRPC создают типы сообщений и клиенты; OpenAPI - модели и HTTP-клиенты; `sqlc` - типизированные функции из SQL; mock-генераторы - тестовые реализации интерфейсов; Wire-подобные инструменты - граф связывания зависимостей. Критерии выбора одинаковы: зрелость входного формата, диагностика, детерминизм, обновляемость, совместимость и стоимость generated API.

# Часть IV. AST и собственный генератор

## 23. От текста к дереву

Чтобы генератор понял Go-код, недостаточно надёжно искать слова регулярным выражением. Слово `type` может встретиться в комментарии или строке, объявления могут быть разбиты переносами, а тип поля может быть сложным выражением. Стандартная библиотека предоставляет парсер и AST - abstract syntax tree.

Для примера

```go
type User struct {
    ID int `json:"id"`
}
```

дерево содержит `ast.File`, внутри declaration `ast.GenDecl` с токеном `TYPE`, затем `ast.TypeSpec` с именем `User`, `ast.StructType` и список `ast.Field`. Тип `int` представлен `ast.Ident`, тег - `ast.BasicLit`.

Пакеты разделяют обязанности:

- `go/token` описывает токены и позиции; `token.FileSet` переводит смещения в файл, строку и столбец;
- `go/parser` создаёт `*ast.File` из файла, строки, `[]byte` или reader;
- `go/ast` определяет узлы и обход дерева;
- `go/types` разрешает имена и проверяет типы;
- `go/format` форматирует итоговый Go-код;
- `go/printer` даёт более низкоуровневую печать дерева;
- `golang.org/x/tools/go/packages` загружает целые пакеты вместе с синтаксисом, типами и зависимостями.

Минимальный анализ:

```go
fset := token.NewFileSet()
file, err := parser.ParseFile(
    fset,
    "model.go",
    nil,
    parser.ParseComments,
)
if err != nil {
    return err
}

for node := range ast.Preorder(file) {
    spec, ok := node.(*ast.TypeSpec)
    if !ok {
        continue
    }
    fmt.Printf("%s: type %s\n",
        fset.Position(spec.Pos()),
        spec.Name.Name,
    )
}
```

`ast.Preorder` возвращает итератор depth-first обхода. `ast.Inspect` - классический callback-вариант. `ast.PreorderStack` дополнительно передаёт стек родительских узлов и позволяет пропускать поддеревья.

## 24. Синтаксис не равен семантике

AST сообщает, как код записан, но не всегда, что он означает. Если тип поля записан `clock.Time`, дерево содержит selector с идентификатором `clock`. Только таблица импортов и type checker сообщат, что `clock` является alias пакета `time`.

Синтаксическое сравнение строк `"time.Time"` сломается при:

```go
import clock "time"

type Event struct {
    At clock.Time
}
```

Оно также не понимает type aliases, именованные типы с одинаковой основой, generic instantiation и assignability. Если генератору достаточно перепечатать синтаксис, AST может быть достаточен. Если нужно решить, можно ли присвоить одно поле другому, следует использовать `go/types` или `go/packages`.

Для печати произвольного `ast.Expr` лучше использовать `go/format` или `go/printer`, а не вручную перечислять несколько вариантов. Ручной `typeToString` почти неизбежно забудет `*ast.IndexExpr`, `*ast.IndexListExpr`, channel, function, interface, anonymous struct или parenthesized expression.

## 25. Пошаговый разбор генератора мапперов

Откроем `cmd/mapper/main.go`. Это сам генератор: его задача - прочитать две структуры, model и DTO, сопоставить поля и создать функции преобразования. Он требует флаги и входные файлы, поэтому команда `go run ./cmd/mapper` без аргументов не является демонстрацией и закономерно вернёт usage с ошибкой. Файл `cmd/mapper-demo/main.go` решает другую задачу: это клиент уже сгенерированных функций, запускаемый командой `go run ./cmd/mapper-demo`.

Шаг первый - входной контракт. Генератор получает флаги `-type`, `-dto`, `-output` и список файлов. Хороший CLI проверяет обязательные параметры, печатает usage в stderr и завершает работу с ненулевым кодом при ошибке.

Шаг второй - создаётся один `token.FileSet`. Все разобранные файлы должны использовать этот набор, чтобы позиции оставались уникальными и диагностика могла показать корректные имя, строку и столбец.

Шаг третий - `parser.ParseFile` строит AST. Флаг `parser.ParseComments` нужен, если генератор читает directives или хочет сохранить комментарии. Ошибка парсинга должна немедленно останавливать генерацию; продолжение после повреждённого файла рискует создать правдоподобный, но неполный результат.

Шаг четвёртый - обход находит `ast.TypeSpec` с требуемыми именами и убеждается, что `TypeSpec.Type` является `*ast.StructType`. Само совпадение имени недостаточно: `type User map[string]any` не является структурой.

Шаг пятый - извлекаются поля. У одного `ast.Field` может быть несколько имён, например `X, Y int`, или ни одного имени для embedded field. Production-генератор обязан либо поддержать эти случаи, либо выдать точную ошибку. Теги представлены строковым literal; безопаснее снять кавычки через `strconv.Unquote`, а затем использовать `reflect.StructTag`, чем вручную обрезать обратные кавычки.

Шаг шестой - сопоставление полей. Учебный генератор сравнивает упрощённые представления типов и выбирает выражения конвертации. Здесь проходит архитектурная граница: синтаксический прототип понятен на лекции, но для настоящей assignability нужен `go/types`.

Шаг седьмой - формируется структура данных для `text/template`: имя пакета, импорты, имена функций, список полей и выражения преобразования. Шаблон отвечает только за вывод. Бизнес-решения - какие поля совпали и какое преобразование выбрать - лучше принять до выполнения шаблона. Тогда шаблон остаётся простым и тестируемым.

Шаг восьмой - шаблон выполняется в `bytes.Buffer`. Нельзя сразу писать целевой файл: ошибка в середине оставит повреждённый результат.

Шаг девятый - `format.Source` проверяет синтаксис и приводит код к стандартному формату. Если форматирование завершилось ошибкой, полезно сохранить или вывести неформатированный буфер в диагностических целях, но не заменять корректный старый generated-файл.

Шаг десятый - атомарная запись результата. Учебный пример использует `os.WriteFile`, что проще, но production-инструмент сначала пишет временный файл рядом с целью, вызывает при необходимости `Sync`, закрывает его и переименовывает.

[Демонстрация, 7 минут. Откройте `mapper_example/user.go`, найдите директиву `go:generate`, затем покажите соответствующий `user_mapper_gen.go`. Проследите одно поле от `ast.Field` через `FieldInfo` и шаблон до присваивания в generated-функции. После этого добавьте простое совместимое поле, запустите генерацию и прочитайте diff. Если менять рабочие файлы на занятии нельзя, покажите ожидаемый diff устно.]

## 26. Ошибки и диагностика генератора

Генератор выполняется в контуре сборки, поэтому строгая ошибка лучше молчаливого предположения. Функция, которая для неизвестного типа возвращает строку `"unknown"`, почти наверняка создаст вторичную, менее понятную ошибку компиляции. Лучше сообщить:

```text
model.go:17:9: mapper: unsupported field type *ast.IndexExpr
```

Хорошая диагностика содержит позицию, имя инструмента, контекст и действие пользователя. Ошибки оборачивают через `%w`, если вызывающий код должен исследовать причину. Несколько независимых ошибок можно собрать, но нельзя продолжать генерацию, если результат становится недостоверным.

Импорты - отдельная сложность. Слепое копирование всех импортов исходного файла создаёт неиспользуемые импорты. Слепое добавление `time` может конфликтовать с локальным именем. Инструменты из `golang.org/x/tools` помогают управлять импортами, но генератор всё равно должен иметь тесты на alias и конфликты имён.

## 27. Тестирование генераторов

У генератора есть минимум три уровня тестов.

Первый - unit-тесты чистой логики: сопоставление поля, разбор тега, выбор конвертации.

Второй - golden-тесты. В `testdata` лежат входной `.go` и ожидаемый `.golden`. Тест запускает генератор, форматирует результат и сравнивает байты. Режим обновления golden-файлов должен быть явным, например через флаг `-update`, иначе ошибка может сама переписать ожидание.

Третий - compilation test. Красивый текст ещё не гарантирует правильность типов. Сгенерированный пакет собирают или загружают через `go/packages`. Полезны также runtime-тесты round trip: `FromDTO(ToDTO(x))` сохраняет ожидаемые поля.

Добавьте негативные случаи: отсутствующий тип, alias import, embedded field, generic type, несовместимые поля, неверный тег, ошибка записи. Для parser и генератора с нетривиальным входом полезен fuzzing: произвольный текст не должен приводить к зависанию или неконтролируемой panic.

Наконец, CI повторяет генерацию и проверяет чистый diff. Это связывает исходники, версию генератора и committed output в один воспроизводимый контракт.

# Заключение

Вернёмся к исходному вопросу: как обработать множество типов, не написав вручную один и тот же код?

Интерфейс подходит, когда нам важно поведение. Мы просим тип реализовать `Write`, `Validate` или `MarshalJSON`, а вызывающий код не интересуется полями.

Generics подходят, когда алгоритм один и тот же, а различия типов можно выразить constraint. Компилятор проверяет каждую инстанциацию, generated-файлы не появляются.

Reflection подходит, когда реальная форма данных становится известна только во время выполнения: универсальный сериализатор, DI-контейнер, RPC-диспетчер, тестовый или диагностический инструмент. За гибкость мы платим динамическими проверками, возможными panic и runtime-стоимостью.

Кодогенерация подходит, когда формы известны во время сборки, повторение велико, а на выполнении нужен обычный статический код. За ранние ошибки и скорость мы платим отдельным инструментом, generated-файлами и требованиями к воспроизводимости.

`unsafe` не является ещё одним способом обобщения. Он нужен, когда задача действительно связана с представлением памяти, ABI или системным интерфейсом. Его использование должно быть локальным, документированным, проверенным на время жизни и границы объектов и подкреплённым измерением.

Если запомнить одну практическую схему, пусть она будет такой: сначала обычный код и интерфейсы; затем generics; reflection - на динамической границе; кодогенерация - для известного заранее повторяемого кода; `unsafe` - только при доказанной низкоуровневой необходимости.
