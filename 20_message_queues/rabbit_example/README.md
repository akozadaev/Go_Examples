# RabbitMQ example for Go

Учебный проект показывает полный путь события через RabbitMQ: публикацию,
маршрутизацию в очередь, получение consumer, повторную попытку после временной
ошибки и перенос безнадёжного сообщения в отдельную очередь для разбора.

В примере используются topic- и direct-exchange, quorum queues, persistent
messages, publisher confirms, ручные подтверждения обработки, prefetch,
отложенные повторы, DLQ, защита от повторной обработки в пределах одного
процесса и корректная остановка приложения.

## Основные понятия

Сначала разберём термины, которые встречаются в коде и логах.

| Термин | Простое объяснение |
|---|---|
| **RabbitMQ, broker** | Сервер-посредник. Он принимает сообщения от приложений, хранит их в очередях и выдаёт обработчикам. |
| **Publisher, producer** | Приложение-отправитель. В проекте это `cmd/publisher`. |
| **Consumer** | Приложение-обработчик. В проекте это `cmd/consumer`. |
| **Message** | Сообщение, которое отправляет publisher: тело в JSON, заголовки и служебные свойства, например `message_id`. |
| **Exchange** | Маршрутизатор внутри RabbitMQ. Publisher отправляет сообщение в exchange, а exchange по правилам направляет его в одну или несколько очередей. Сам exchange сообщения не хранит. |
| **Queue** | Очередь, в которой RabbitMQ хранит сообщения до их обработки. |
| **Routing key** | Строка-маршрут, указанная при публикации. Exchange сопоставляет её с правилами привязки очередей. |
| **Binding** | Правило, связывающее exchange с очередью. Оно определяет, какие routing keys ведут в эту очередь. |
| **Delivery** | Один факт передачи сообщения из очереди конкретному consumer. В Go значение `amqp.Delivery` содержит тело, заголовки и служебный номер доставки. Повторно выданное сообщение создаёт новый delivery. |
| **Channel** | Логический AMQP-канал внутри TCP-соединения с RabbitMQ. Публикации, deliveries и подтверждения выполняются через channel. Это не Go channel. |
| **Ack** | Положительное подтверждение от consumer: «этот delivery успешно обработан». Получив ack, RabbitMQ удаляет сообщение из очереди. |
| **Nack** | Отрицательное подтверждение от consumer. Параметр `requeue` указывает, надо ли сразу вернуть сообщение в ту же очередь. |
| **Unacked** | RabbitMQ уже передал сообщение consumer, но ещё не получил ни ack, ни nack. Такое сообщение считается находящимся в обработке. При закрытии соединения или channel оно снова становится доступным для доставки. |
| **Publisher confirm** | Подтверждение от RabbitMQ издателю, что broker принял на себя ответственность за опубликованное сообщение. Оно не означает, что consumer получил или обработал сообщение. |
| **`mandatory=true` и `basic.return`** | Дополнительная проверка маршрута. Если ни одна очередь не подходит, RabbitMQ возвращает публикацию издателю через `basic.return`. Положительный publisher confirm сам по себе не выявляет отсутствие подходящей очереди. |
| **TTL** | Время жизни сообщения в очереди. В retry-очереди TTL используется как таймер перед повторной попыткой. |
| **DLX** | Dead-letter exchange - exchange, в который RabbitMQ направляет сообщение, отклонённое без возврата в исходную очередь или просроченное по TTL. |
| **DLQ** | Dead-letter queue - очередь для сообщений, которые автоматически обработать не удалось. Их можно изучить вручную. |
| **Prefetch** | Ограничение количества deliveries, которые RabbitMQ может выдать consumer одновременно и оставить без подтверждения. |
| **Quorum queue** | Тип реплицируемой очереди RabbitMQ. На локальном стенде из одного узла она не даёт отказоустойчивости, но позволяет показать production-подход и at-least-once dead-lettering. |
| **Идемпотентность** | Способность безопасно получить одно логическое событие несколько раз и применить бизнес-изменение только один раз. |

## Два разных подтверждения

Publisher confirm и consumer ack решают разные задачи и передаются в разных
частях маршрута:

```text
publisher  -- публикация -->  RabbitMQ  -- delivery -->  consumer
publisher  <-- confirm -----  RabbitMQ  <-- ack --------  consumer
```

Publisher confirm отвечает только на вопрос: «Принял ли RabbitMQ публикацию?»
Consumer ack отвечает на другой вопрос: «Закончил ли consumer обработку
полученного delivery?» Между этими событиями может пройти произвольное время.

Например, RabbitMQ может подтвердить публикацию, сохранить сообщение в очереди,
а consumer обработает его через минуту. Возможна и обратная ситуация: consumer
успел обработать сообщение и отправил ack, но соединение оборвалось раньше, чем
RabbitMQ получил подтверждение. Тогда broker выдаст сообщение повторно. Поэтому
обработчик обязан учитывать дубликаты.

## Топология примера

Топология - это набор exchange, очередей и связей между ними.

| Имя | Тип | Назначение |
|---|---|---|
| `orders.events` | topic exchange | Принимает обычные события заказов и направляет их в рабочие очереди. |
| `orders.created.worker` | quorum queue | Основная очередь consumer. |
| `orders.retry` | direct exchange | Маршрутизирует копию временно не обработанного сообщения в retry-очередь. Это не хранилище и не таймер. |
| `orders.created.retry` | quorum queue с TTL | Хранит сообщение в течение `RETRY_DELAY`. После истечения TTL RabbitMQ направляет его обратно в `orders.events`. Именно эта очередь создаёт задержку. |
| `orders.dlx` | direct exchange | Маршрутизирует окончательно отклонённые сообщения в DLQ. |
| `orders.created.dead` | quorum queue | DLQ для ручного анализа сообщений, которые нельзя обработать автоматически. |

Основной маршрут выглядит так:

```text
cmd/publisher
    |
    | routing key: orders.created
    v
orders.events (topic exchange)
    |
    v
orders.created.worker (main queue)
    |
    | delivery
    v
cmd/consumer
```

Exchange выбирает очередь по routing key и binding. После помещения сообщения в
`orders.created.worker` RabbitMQ выдаёт его consumer как delivery. До получения
ack сообщение остаётся в состоянии unacked.

## Успешная обработка

При успешном сценарии выполняются следующие действия:

1. Publisher отправляет событие в `orders.events` с routing key
   `orders.created`.
2. Exchange направляет сообщение в `orders.created.worker`.
3. RabbitMQ подтверждает публикацию publisher через publisher confirm.
4. RabbitMQ передаёт сообщение consumer как `amqp.Delivery`.
5. Consumer разбирает JSON и выполняет обработчик.
6. После успешной обработки consumer вызывает `delivery.Ack(false)`.
7. RabbitMQ удаляет подтверждённое сообщение из основной очереди.

Ручной ack отправляется после бизнес-обработки. Если подтвердить delivery до
неё, то при аварии consumer сообщение уже будет удалено и повторить обработку
станет невозможно.

## Повтор после временной ошибки

Временная ошибка означает, что повторная попытка может помочь: например,
зависимый сервис кратковременно недоступен. Consumer не может просто оставить
delivery в основной очереди с немедленным `requeue=true`, потому что сообщение
будет выдаваться снова без паузы и создаст быстрый бесконечный цикл.

Вместо этого пример делает отложенный повтор:

```text
consumer
    |
    | публикует копию с увеличенным x-retry-count
    v
orders.retry (retry exchange)
    |
    v
orders.created.retry (retry queue, TTL = RETRY_DELAY)
    |
    | TTL истёк: RabbitMQ выполняет dead-lettering
    v
orders.events
    |
    v
orders.created.worker
```

Последовательность особенно важна:

1. Consumer получает исходный delivery из основной очереди.
2. Обработчик возвращает временную ошибку.
3. Consumer создаёт копию сообщения и увеличивает заголовок
   `x-retry-count`.
4. Копия публикуется в `orders.retry` с `mandatory=true`.
5. Приложение ждёт publisher confirm и проверяет, что RabbitMQ не вернул
   публикацию через `basic.return`.
6. Только после успешной публикации копии consumer отправляет ack для исходного
   delivery. Исходное сообщение удаляется из основной очереди.
7. Копия ждёт в `orders.created.retry` до истечения TTL.
8. RabbitMQ направляет её обратно через `orders.events` в основную очередь, и
   consumer получает новый delivery.

Таким образом, **retry exchange** - это всего лишь отдельный маршрутизатор для
повторных сообщений. Он не хранит их и не создаёт задержку. Задержку создаёт
**retry queue** с TTL.

Если публикацию retry-копии подтвердить не удалось, consumer не делает ack
исходного delivery. При завершении процесса или закрытии AMQP channel RabbitMQ
вернёт исходное сообщение из состояния unacked в основную очередь и позднее
выдаст его снова.

Полностью исключить дубликат всё равно нельзя. Возможны два характерных случая:

- RabbitMQ принял retry-копию, но приложение не дождалось confirm из-за обрыва
  сети. Исходный delivery останется unacked и будет выдан повторно, хотя копия
  уже могла попасть в retry-очередь.
- RabbitMQ подтвердил retry-копию, consumer отправил ack исходного delivery, но
  ack потерялся при разрыве соединения. Broker повторно выдаст оригинал, а
  retry-копия тоже продолжит свой маршрут.

Такая гарантия называется **at-least-once delivery**: система старается не
потерять сообщение, но одно логическое событие может быть доставлено более
одного раза. Поэтому `message_id` и идемпотентный обработчик являются частью
надёжной схемы, а не необязательной оптимизацией.

## Постоянная ошибка и DLQ

Постоянная ошибка означает, что повтор без изменения сообщения или программы не
поможет. Примеры: некорректный JSON, нарушение бизнес-правила или исчерпание
`MAX_RETRIES`.

Consumer вызывает `delivery.Nack(false, false)`: первый `false` означает
«подтвердить только этот delivery», второй - «не возвращать его прямо в основную
очередь». У `orders.created.worker` настроен dead-letter exchange, поэтому
RabbitMQ переносит сообщение по маршруту:

```text
orders.created.worker
    |
    | nack с requeue=false
    v
orders.dlx
    |
    v
orders.created.dead (DLQ)
```

Для основной и retry quorum queues включён **at-least-once dead-lettering**.
При таком переносе исходная очередь не удаляет сообщение, пока целевая очередь
не подтвердила его приём. Для этой стратегии RabbitMQ требует настройку overflow
`reject-publish`, которая задана в топологии примера.

DLQ не исправляет сообщение и не повторяет его автоматически. Это место для
ручного анализа: оператор может определить причину ошибки, исправить данные или
код и только затем отдельно выполнить контролируемый replay.

## Требования

- Go 1.26.4;
- Docker с Docker Compose;
- RabbitMQ 4.2 Management из `compose.yaml`.

## Быстрый запуск

Запустите RabbitMQ и consumer:

```bash
docker compose up -d --wait
go run ./cmd/consumer
```

В другом терминале опубликуйте событие:

```bash
go run ./cmd/publisher \
  --order-id order-42 \
  --customer-id customer-7 \
  --amount 159900 \
  --currency RUB
```

Web-интерфейс RabbitMQ Management доступен по адресу
<http://localhost:15672>. Логин и пароль локального окружения: `app` / `app`.

Приложения читают настройки непосредственно из переменных окружения. Файл
`.env` автоматически не загружается. Доступные значения и локальные значения по
умолчанию перечислены в `.env.example`.

## Демонстрационные сценарии

### Успешная обработка

```bash
go run ./cmd/publisher --order-id order-success
```

### Две временные ошибки, затем успех

```bash
go run ./cmd/publisher \
  --order-id order-retry \
  --demo-failure transient \
  --fail-attempts 2
```

Consumer дважды создаст retry-копию. Перед каждой следующей попыткой сообщение
проведёт `RETRY_DELAY` в retry-очереди.

### Постоянная ошибка

```bash
go run ./cmd/publisher \
  --order-id order-permanent \
  --demo-failure permanent
```

Сообщение будет отклонено без немедленного возврата и попадёт в DLQ.

### Некорректный JSON

```bash
go run ./cmd/publisher --order-id order-malformed --malformed
```

Consumer не сможет разобрать тело и направит сообщение в DLQ.

### Исчерпание повторов

Если число временных ошибок больше `MAX_RETRIES`, после разрешённого количества
повторов сообщение попадёт в DLQ:

```bash
MAX_RETRIES=2 go run ./cmd/consumer
```

В другом терминале:

```bash
go run ./cmd/publisher \
  --order-id order-exhausted \
  --demo-failure transient \
  --fail-attempts 10
```

`MAX_RETRIES` читает consumer, поэтому переменную нужно задавать именно при его
запуске. Технические заголовки `x-demo-failure` и `x-demo-fail-attempts` нужны
только для воспроизводимой демонстрации и не входят в бизнес-контракт JSON.

## Просмотр DLQ

Команда без `--ack` получает один delivery из DLQ, показывает сообщение и
возвращает его в ту же очередь:

```bash
go run ./cmd/dlq-reader
```

Чтобы после просмотра подтвердить delivery и удалить сообщение из DLQ:

```bash
go run ./cmd/dlq-reader --ack
```

У DLQ отключён стандартный quorum delivery limit. Поэтому многократный просмотр
с возвратом не удалит сообщение после 20 доставок. Это осознанное исключение для
очереди ручного разбора; основная очередь сохраняет защиту RabbitMQ от
бесконечной доставки проблемного сообщения.

В production просмотр и повторная публикация из DLQ требуют авторизации,
аудита, сокрытия чувствительных данных и отдельного регламента. Учебный CLI
намеренно не выполняет автоматический replay.

## Дубликаты и идемпотентность

Флаг `--message-id` позволяет дважды отправить одно логическое событие:

```bash
go run ./cmd/publisher --order-id order-duplicate --message-id demo-event-1
go run ./cmd/publisher --order-id order-duplicate --message-id demo-event-1
```

Consumer запоминает обработанные идентификаторы в `MemoryProcessedStore` и не
выполняет повторное бизнес-действие в пределах жизни процесса. Это только
учебная демонстрация: после перезапуска consumer память очищается.

В production обработчик обычно должен в одной транзакции базы данных:

1. вставить пару `(consumer_name, message_id)` в таблицу
   `processed_messages` с уникальным ограничением;
2. выполнить бизнес-изменение;
3. зафиксировать транзакцию;
4. только после успешного commit отправить RabbitMQ ack.

Если вставка нарушила уникальное ограничение, событие уже было обработано:
бизнес-действие повторять не нужно, но текущий delivery можно подтвердить.

## Конфигурация

| Переменная | Значение по умолчанию | Назначение |
|---|---:|---|
| `AMQP_URL` | `amqp://app:app@localhost:5672/app` | Адрес RabbitMQ и virtual host `/app` |
| `PREFETCH` | `8` | Не более восьми одновременно выданных, но ещё не подтверждённых deliveries |
| `RETRY_DELAY` | `5s` | Время хранения сообщения в retry-очереди перед новой попыткой |
| `MAX_RETRIES` | `3` | Максимальное число повторов после первой попытки |
| `PUBLISH_TIMEOUT` | `10s` | Предельное ожидание публикации и publisher confirm |
| `SHUTDOWN_TIMEOUT` | `10s` | Предельное время корректной остановки consumer |

`RETRY_DELAY` становится аргументом уже созданной очереди. RabbitMQ не позволяет
объявить очередь с тем же именем, но другим TTL. После изменения значения
`orders.created.retry` нужно мигрировать или удалить вместе с локальными
данными:

```bash
docker compose down -v
```

Параметр `-v` удаляет Docker volume RabbitMQ, включая все локальные сообщения.

## Проверки

```bash
go test ./...
go test -race ./...
go build ./...

# Требует запущенный RabbitMQ
go test -tags=integration ./internal/messaging
```

Unit-тесты не требуют RabbitMQ. Интеграционные тесты используют настоящий broker
из `compose.yaml`. Отдельный тест проверяет, что обязательная публикация
(`mandatory=true`) без подходящего binding возвращается publisher как ошибка.

## Ограничения учебного примера

- Соединения автоматически не восстанавливаются. При сетевой ошибке процесс
  завершается и должен быть перезапущен supervisor или orchestrator.
- Истечение времени ожидания publisher confirm даёт неопределённый результат:
  RabbitMQ мог принять сообщение, хотя приложение не получило подтверждение.
- Один `Publisher` выполняет публикации последовательно и ждёт каждый confirm.
  Это удобно для изучения, но ограничивает пропускную способность.
- DLX и TTL заданы аргументами очередей. В production изменяемые настройки часто
  задают через RabbitMQ policies.
- Quorum queue на одном локальном узле не обеспечивает отказоустойчивость. Для
  неё нужен кластер с корректно выбранным нечётным числом реплик.
- Учебные логин, пароль и открытый management port нельзя переносить в
  production.
