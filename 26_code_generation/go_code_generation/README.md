# Лекция 26. Кодогенерация в Go 1.26

Продолжительность этой части — около 65 минут. Вместе с предыдущей темой получается двухчасовое занятие: примерно 55 минут на reflection, 5 минут на перерыв и 60 минут на кодогенерацию. Последние 10–15 минут этой части отведены разбору собственного AST-генератора из `cmd/mapper`.

## От runtime-универсальности к коду времени сборки

В предыдущей части мы увидели цену reflection. Универсальная функция может исследовать неизвестный тип, но компилятор уже не проверяет имена полей и многие ошибки проявляются только на выполнении. Кодогенерация предлагает иной обмен: специальная программа исследует описание типов заранее и пишет обычный Go-код. После этого генератор в production-процессе не участвует. Результат компилируется, тестируется и профилируется как ручной код.

Кодогенерация — не особая фаза компилятора Go и не макросистема. Генератор является обычной программой: читает схему, исходный Go-код, SQL, protobuf или шаблон и создаёт файлы. Компилятор видит только итоговые `.go`-файлы.

Эта техника особенно полезна, когда вход известен во время сборки, результат велик и однообразен, а ошибка должна стать ошибкой сборки. Типичные примеры — клиенты API, protobuf, ORM-запросы, mock-реализации, методы перечислений, сериализаторы и преобразования DTO.

Генерация имеет цену. В репозитории появляется ещё один инструмент и его версия; диффы могут быть шумными; отладка требует понимать и вход, и генератор, и результат. Маленькую функцию проще написать вручную. Generics лучше, когда один алгоритм можно выразить один раз без создания исходников. Reflection лучше, когда набор типов становится известен лишь во время выполнения.

## Что на самом деле делает `go generate`

В Go-файле размещают директиву без пробела после `//`:

```go
//go:generate stringer -type=Status -trimprefix=Status
```

Команда `go generate ./...` находит такие строки и последовательно запускает указанные процессы в директории пакета. Она не входит в `go build` и `go test`; её нужно вызывать явно. Это принципиально: обычная сборка должна работать по уже существующим исходникам и не менять рабочее дерево.

`go generate` не является shell. Оно разбивает строку на аргументы, обрабатывает строки в кавычках по правилам Go и подставляет переменные. Конвейеры, перенаправления и условные команды требуют явного вызова оболочки и ухудшают переносимость. Доступны `$GOFILE`, `$GOLINE`, `$GOPACKAGE`, `$GOARCH`, `$GOOS`, а `$DOLLAR` позволяет получить знак доллара. Команда выполняется с переменной `GOROOT`, соответствующей запускающему `go`.

Полезные режимы:

```bash
go generate -n ./...             # показать команды, не выполнять
go generate -x ./...             # печатать выполняемые команды
go generate -run stringer ./...  # выбрать директивы regexp-ом
go generate -skip easyjson ./... # исключить директивы regexp-ом
```

Если генератор завершился с ошибкой, остальные директивы текущего пакета не исполняются. Порядок пакетов, файлов и директив определён документацией, но строить сложный граф зависимостей на этом не стоит: `go generate` не знает, какой выход зависит от какого входа, и ничего не кэширует.

Каждый сгенерированный Go-файл должен до первого обычного текста содержать строку формы:

```go
// Code generated by mygenerator; DO NOT EDIT.
```

Эту каноническую пометку распознают инструменты Go. Она говорит людям, анализаторам и системам ревью, что исправлять нужно генератор или его вход, а не выходной файл.

## Воспроизводимость — часть контракта

Директива `stringer` предполагает, что бинарник есть в `PATH`. Для учебного компьютера это удобно, но команда `go install ...@latest` делает будущую генерацию зависимой от будущей версии. В рабочем проекте версии инструментов фиксируют.

В современных модулях Go можно записать инструмент директивой `tool` в `go.mod` и запускать его через `go tool`; зависимости инструмента тогда управляются модулем. Другой распространённый вариант — директива `go run module/path@version ...`. В обоих случаях важно, чтобы версия была явно обозрима. Сгенерированные файлы обычно коммитят: пользователь библиотеки не обязан иметь генератор, а CI может повторить генерацию и проверить чистый diff.

Хорошая CI-проверка концептуально делает следующее:

```text
go generate ./...
gofmt/gofumpt — если это часть контракта проекта
go test ./...
проверка отсутствия незакоммиченного diff
```

Генератор должен быть детерминирован. Нельзя без необходимости встраивать текущее время, случайные идентификаторы или абсолютные пути. Map перед выводом нужно сортировать. Запись лучше выполнять атомарно: сформировать и отформатировать всё в памяти, записать временный файл рядом с целью и заменить цель только после успеха.

## Готовые инструменты

### `stringer`

`golang.org/x/tools/cmd/stringer` генерирует метод `String()` для именованного целочисленного типа. В `stringer_example/status.go` задан `Status` и четыре константы. После генерации появляется обычный метод, удовлетворяющий `fmt.Stringer`.

```go
//go:generate stringer -type=Status -trimprefix=Status
```

`stringer` хорошо работает не только с последовательным `iota`; утверждение, что последовательность обязательна, неверно. Для одинаковых числовых значений выбирается одно имя, поэтому алиасы нужно обсуждать как часть контракта. Флаги `-linecomment` и `-trimprefix` позволяют управлять внешним текстом. Не следует превращать `String()` в стабильный сетевой протокол автоматически: переименование Go-константы изменит строку. Для API лучше задать явное представление и тесты совместимости.

### `jsonenums`

`github.com/campoy/jsonenums` показывает популярный паттерн: генерация `MarshalJSON` и `UnmarshalJSON` для enum. Учебный пример расположен в `jsonenums_example`. Однако проект давно обновляется редко, поэтому это хороший повод обсудить критерии выбора зависимости: активность, лицензия, совместимость с текущим Go, корректность ошибок для неизвестных значений, воспроизводимость версии.

В новом production-коде маленький enum нередко лучше реализовать вручную или собственным простым генератором, особенно если его JSON-строки являются публичным контрактом. Наличие библиотеки в лекции — демонстрация подхода, а не безусловная рекомендация.

### `easyjson`

`github.com/mailru/easyjson` генерирует специализированные JSON-кодировщики. Исходные структуры находятся в `easyjson_example/user.go`, а `user_easyjson.go` показывает объём результата. Преимущество не надо объявлять заранее числом «в N раз»: оно зависит от данных, версии стандартной библиотеки, архитектуры и операции. Именно поэтому рядом лежит `benchmark_test.go`.

```bash
go test -bench=. -benchmem ./easyjson_example
```

Сравнивайте одинаковые данные, проверяйте корректность результата и смотрите не только `ns/op`, но и `B/op`, `allocs/op`. Метод `MarshalJSON`, созданный easyjson, реализует стандартный интерфейс, поэтому вызов `encoding/json.Marshal(user)` может также попасть в сгенерированный метод. Для честного сравнения иногда нужны отдельные зеркальные типы без методов; это следует учитывать при интерпретации учебного бенчмарка.

Кодогенератор может отличаться от `encoding/json` в пограничных случаях. Перед заменой проверяют семантику неизвестных полей, регистр имён, числа, `omitempty`/`omitzero`, пользовательские маршалеры и streaming. Производительность никогда не отменяет тесты совместимости.

### `impl`

`github.com/josharian/impl` печатает заготовки методов, необходимые типу для реализации интерфейса. Это интерактивный помощник, а не обязательный этап каждой сборки. В `impl_example` заготовки уже превращены в осмысленную реализацию `FileLogger`.

Существенная граница: генератор способен создать сигнатуры, но не знает бизнес-семантику. Заглушка, которая компилируется и молча возвращает нулевое значение, часто хуже явной ошибки. После генерации методы нужно реализовать и добавить compile-time проверку:

```go
var _ Logger = (*FileLogger)(nil)
```

Кроме этих примеров, в экосистеме распространены генераторы protobuf/gRPC, OpenAPI, SQL (`sqlc`), mock-объектов и dependency injection. Выбирать следует не по длине списка, а по зрелости формата входа, качеству diagnostics, стабильности результата и стоимости обновления.

## AST: исходный код как дерево

Текст Go сначала разбирается на токены, затем на абстрактное синтаксическое дерево. Для объявления

```go
type User struct {
    ID int `json:"id"`
}
```

важны узлы `ast.GenDecl` с токеном `TYPE`, `ast.TypeSpec`, `ast.StructType`, список `ast.Field` и выражение типа `ast.Ident`. Пакеты стандартной библиотеки разделяют обязанности:

- `go/token` описывает токены и позиции; `token.FileSet` связывает смещения с файлами и строками;
- `go/parser` строит `*ast.File` из исходника;
- `go/ast` задаёт типы узлов и способы обхода;
- `go/types` проверяет и разрешает типы, если одной синтаксической формы мало;
- `go/format` форматирует готовый Go-код стандартным способом;
- `golang.org/x/tools/go/packages` загружает пакеты вместе с файлами, типами и зависимостями.

Минимальный анализатор:

```go
fset := token.NewFileSet()
file, err := parser.ParseFile(fset, "model.go", nil, parser.ParseComments)
if err != nil {
    return err
}
for node := range ast.Preorder(file) {
    if ts, ok := node.(*ast.TypeSpec); ok {
        fmt.Println("type", ts.Name.Name, "at", fset.Position(ts.Pos()))
    }
}
```

В Go 1.23 появился итератор `ast.Preorder`; если нужен стек родителей и управление спуском, в современном API есть `ast.PreorderStack`. Классический `ast.Inspect` по-прежнему подходит для простого depth-first обхода.

AST хранит синтаксис, но не всегда смысл. Узел `*ast.Ident` с именем `ID` сам по себе не сообщает, из какого пакета взят тип; alias-импорты, dot-import и generic instantiation усложняют картину. Строковое сравнение `time.Time` работает в маленьком примере, но сломается при `import clock "time"`. Если генератор должен понимать идентичность типов и assignability, нужен `go/types` или загрузка через `go/packages`.

## Разбор практического генератора мапперов

`cmd/mapper/main.go` — центральный практический пример. Директива в модели запускает его через `go run`, передаёт имена model/DTO, выходной файл и входные файлы. Генератор:

1. разбирает файлы `parser.ParseFile`;
2. находит нужные `TypeSpec` и убеждается, что это структуры;
3. извлекает поля и теги;
4. сопоставляет поля модели и DTO;
5. выбирает выражения преобразования;
6. исполняет `text/template` в буфер;
7. пропускает результат через `format.Source`;
8. записывает `.go`-файл.

Это правильная учебная вертикаль: видны и AST-вход, и шаблон, и типизированный выход. Обратите внимание на маркер `Code generated`, обработку ошибок и форматирование до записи.

Теперь критический взгляд. Функция `typeToString` понимает лишь часть возможных `ast.Expr`; Go-типы включают каналы, функции, интерфейсы, анонимные структуры, generic instantiation и скобки. Сбор всех импортов может внести неиспользуемый импорт. Поля сопоставляются по упрощённому имени и синтаксическому тексту, а не по информации `go/types`. Несколько файлов обязаны принадлежать одному пакету, но это следует проверить. Выход записывается напрямую, поэтому ошибка записи может оставить частичный файл. Эти ограничения допустимы для лекции, если они названы, но production-генератор должен либо поддерживать случаи, либо завершаться с точной диагностикой позиции.

Практическое правило: неизвестный синтаксис нельзя превращать в строку `"unknown"` и продолжать. Лучше вернуть ошибку вида `model.go:17:9: unsupported field type *ast.IndexExpr`. Генераторы живут в сборочном контуре, и строгий отказ здесь полезнее правдоподобного неверного кода.

Шаблон и AST — не конкуренты. AST удобно анализировать и иногда строить; `text/template` удобно использовать для больших повторяющихся фрагментов. Какой бы способ ни выбран, итог следует пропустить через `go/format`. При модификации существующего дерева с комментариями нужно особенно внимательно работать с позициями: комментарии привязаны к token positions, а не магически к узлам.

## Практическая последовательность занятия

Сначала посмотрите команды без исполнения:

```bash
go generate -n ./...
```

Затем изучите `stringer_example/status.go` и ожидаемый `status_string.go`; обсудите, является ли имя константы частью API. После этого запустите JSON-бенчмарк и проверьте, действительно ли сравниваются разные реализации. Наконец измените одно поле в `mapper_example`, повторите генерацию и прочитайте diff сгенерированного файла.

Для собственного упражнения добавьте генератору ошибку на неизвестный тип вместо `"unknown"`, выведите позицию через `FileSet`, затем напишите тест на golden-файл. Golden-тест запускает генератор на фиксированном входе и сравнивает результат с ожидаемым `.golden`; отдельный тест компилирует сгенерированный пакет. Это проверяет и текстовый контракт, и смысл.

## Итог двух тем

Reflection и кодогенерация решают похожую задачу обобщения в разные моменты времени. Reflection изучает реальное значение в runtime и подходит открытому множеству типов. Генератор изучает описание заранее и выпускает статический код, поэтому ошибки раньше, а горячий путь проще. Generics занимают третью позицию: дают статический повторно используемый алгоритм без генерации файлов.

Выбор можно сформулировать так: интерфейс — когда важно поведение; generics — когда одинаков алгоритм; reflection — когда неизвестна runtime-форма; кодогенерация — когда формы известны во время сборки, но ручной статический код слишком повторяем. `unsafe` в эту шкалу не входит: он нужен лишь там, где требуется контролировать представление памяти.
